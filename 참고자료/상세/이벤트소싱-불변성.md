# 이벤트 소싱/불변성 — 요구사항과 Medusa 구현 대응 분석

요구사항: "결제액 관련 요소는 이벤트 소싱 관점에서 불변이 적합. 변경 시 새로운 내역을 쌓아야 함"

상위: [README.md](../개요/README.md)

---

## 요약

Medusa는 이 철학을 두 가지 구조로 구현한다.

1. **스냅샷 분리**: 주문 시점의 상품 정보·단가를 `OrderLineItem`(불변)에 박아두고, 이후 상태 변화는 `OrderItem`(가변)에 버전별로 추적한다.
2. **`OrderChange` + `OrderChangeAction` 패턴**: 주문 변경을 직접 UPDATE하지 않고, 변경 의도를 `OrderChangeAction` 레코드로 쌓은 뒤 확정 시점에 한꺼번에 반영한다.

## 1. 스냅샷 불변 구조

### 이중 레이어

```
OrderLineItem (불변 스냅샷)          OrderItem (버전별 상태)
─────────────────────────────       ──────────────────────────────
unit_price = 25000                  version = 1
product_title = "캐시미어 니트"       quantity = 2
variant_sku = "CSM-001-S"           fulfilled_quantity = 0
is_discountable = true              return_requested_quantity = 0
(이후 상품 정보가 변경돼도 영향 없음)  return_received_quantity = 0
```

파일:
- [`packages/modules/order/src/models/line-item.ts`](../../packages/modules/order/src/models/line-item.ts)
- [`packages/modules/order/src/models/order-item.ts`](../../packages/modules/order/src/models/order-item.ts)

`OrderLineItem`에는 `version` 필드가 없다. 한번 INSERT되면 이후 변경되지 않는다.

`OrderItem`은 `Order.version`과 동기화된다. 주문에 변경이 생길 때마다 새 버전의 `OrderItem` 행이 INSERT된다.

### `formatOrder()`의 병합

[`packages/modules/order/src/utils/transform-order.ts`](../../packages/modules/order/src/utils/transform-order.ts)

조회 시 `formatOrder()`가 `OrderItem.item` (→ `OrderLineItem`)을 스프레드해서 API 응답 객체를 만든다. 외부에서는 두 테이블이 분리된 것을 알 수 없다.

## 2. `OrderChange` + `OrderChangeAction` 패턴

### 쌓는(append-only) 구조

주문 변경이 필요할 때 기존 레코드를 UPDATE하지 않는다.

```
변경 요청 발생
  → OrderChange 레코드 생성 (status: PENDING)
  → OrderChangeAction 레코드 INSERT (ordering 순서 부여)
       action: "RETURN_ITEM"
       details: { reference_id: "ordli_abc", quantity: 1 }
       amount: 25000
       applied: false   ← 아직 미적용
```

파일:
- [`packages/modules/order/src/models/order-change.ts`](../../packages/modules/order/src/models/order-change.ts)
- [`packages/modules/order/src/models/order-change-action.ts`](../../packages/modules/order/src/models/order-change-action.ts)

### 적용(confirm) 시점의 일괄 처리

`confirmOrderChanges` 워크플로우가 실행되면:

1. `OrderChange.status` → `CONFIRMED`
2. `applyOrderChanges_()` 호출 → `OrderChangeAction.applied = true` 일괄 갱신
3. `Order.version` 증가
4. 새 버전의 `OrderItem`, `OrderShipping`, `OrderSummary` 행 INSERT

파일: [`packages/modules/order/src/services/order-module-service.ts`](../../packages/modules/order/src/services/order-module-service.ts) — `applyOrderChanges_()` 메서드

### 미리보기(`previewOrderChange`)

`previewOrderChange(orderId)`는 DB에 저장하지 않고 메모리에서만 액션을 시뮬레이션한다.

```
order + 미적용 OrderChangeAction[]
  → applyChangesToOrder() (메모리 계산)
  → decorateCartTotals() (합계 계산)
  → getSummaryFromOrder() (pending_difference 계산)
```

파일: [`packages/modules/order/src/utils/apply-order-changes.ts`](../../packages/modules/order/src/utils/apply-order-changes.ts)

## 3. `OrderSummary`의 불변 이력 추적

`OrderSummary`는 `version`별로 행이 생성된다. 즉 주문 이력 전체가 `version` 번호로 조회 가능하다.

`totals` JSON에서 `pending_difference`의 의미:

```
pending_difference = current_order_total - transaction_total
```

- 양수: 고객이 추가로 내야 할 금액
- 음수: 환불해야 할 금액
- 0: 결제 완료 상태

`transaction_total`은 `OrderTransaction` 행들의 합계다. 결제는 양수, 환불은 음수로 INSERT된다 — UPDATE 없이 쌓기만 한다.

파일: [`packages/modules/order/src/models/transaction.ts`](../../packages/modules/order/src/models/transaction.ts)

## 4. 요구사항과의 Gap

요구사항에서 "이벤트 소싱"이 명시된 항목은 결제액 관련 요소. Medusa가 커버하는 범위와 미커버 범위:

| 항목 | Medusa 구현 | 비고 |
|------|------------|------|
| 주문 시점 단가 불변 | ✅ `OrderLineItem` 스냅샷 | |
| 주문 변경 이력 | ✅ `OrderChangeAction.ordering` 순서 보존 | |
| 결제/환불 이력 | ✅ `OrderTransaction`에 append-only | |
| 크레딧(포인트) 이력 | ✅ `OrderCreditLine`에 append-only | |
| 할인 적용 이력 | ✅ `OrderLineItemAdjustment` 행으로 저장 | |
| 배송비 변경 이력 | 부분적 — `flat` 타입 배송비는 `OrderShippingMethod.amount` UPDATE | `calculated` 타입만 `OrderChangeAction`으로 추적 |
| 프로모션 제거 이력 | `PROMOTION_REMOVE` 액션이 있으나 자동 트리거 범위 제한 | 부분 반품 후 무료배송 조건 이탈 시 자동 처리 없음 |
