# 부분 취소·환불 처리 — Medusa 구현 방식

[← 목록](./README.md)

요구사항: 취소·환불 범위에 따른 증가·차감 요소 재계산 / 반품 후 무료배송 조건 이탈 시 배송비 복원

---

## 반품·환불 흐름

Medusa의 반품은 **OrderChange 패턴**으로 처리된다. 직접 레코드를 수정하지 않고, 변경 의도를 OrderChangeAction으로 쌓은 뒤 confirm 단계에서 반영한다.

```
beginReturnOrderWorkflow     → Return(OPEN) + OrderChange 생성
requestItemReturnWorkflow    → OrderChangeAction(RETURN_ITEM) 추가
confirmReturnRequestWorkflow → ReturnItem 생성 + Return(REQUESTED) + 결제 컬렉션 갱신
confirmReturnReceiveWorkflow → 재고 복원 + Return(RECEIVED/PARTIALLY_RECEIVED)
refundPaymentWorkflow        → Refund 생성 + 결제 프로바이더 환불 + OrderTransaction(음수) 기록
```

참고: [사용자 여정 분析 11-반품-부분환불](../사용자 여정 분析/11-반품-부분환불/README.md)

## 증가·차감 요소 재계산 범위

### 환불 한도 검증

`validateRefundPaymentExceedsCapturedAmountStep`:

```
captured_total - refunded_total - 신규환불요청액 ≥ -epsilon
```

이 검증을 통해 캡처 총액을 초과하는 환불을 방지한다.

### 결제 컬렉션 갱신

`confirmReturnRequestWorkflow` Step 5에서 `createOrUpdateOrderPaymentCollectionWorkflow`가 호출되어 미수금(환불 가능 금액)이 재계산된다.

### OrderTransaction으로 불변 이력 관리

환불이 실행될 때마다 `OrderTransaction`이 음수 금액으로 추가된다. 기존 레코드를 수정하지 않고 새 레코드를 추가하는 방식이다 — 요구사항의 "결제 관련 기록은 수정하지 않는다" 원칙과 일치한다.

| 이벤트 | `reference` | `amount` |
|--------|-------------|----------|
| 결제 캡처 | `"capture"` | 양수 |
| 환불 | `"refund"` | 음수 |

### 복수 결제 동시 환불

`refundPaymentsWorkflow`는 여러 Payment를 `Promise.all`로 병렬 처리한다. 개별 실패는 로그로만 남기고 전체 흐름은 이어간다.

## 무료배송 조건 이탈 시 배송비 복원

**요구사항**: 부분 반품 후 주문금액이 무료배송 기준 이하로 내려갔을 때, 취소된 상품의 가격보다 배송비가 더 큰 경우를 고려해야 한다.

**Medusa 현황 (사실)**: 반품 확정 시 배송비를 자동으로 재계산하는 로직이 없다.

- 주문 완료 시 `OrderShippingMethod`가 스냅샷으로 고정된다.
- `confirmReturnRequestWorkflow`와 `confirmReturnReceiveWorkflow`는 결제 컬렉션만 갱신하고, 배송비 금액을 재산정하지 않는다.
- `OrderShippingMethodAdjustment`(배송비 할인 조정)도 반품 후 자동 변경되지 않는다.

**결론 (사실)**: 이 케이스는 Medusa 기본 구현으로는 처리되지 않는다. 별도 로직이 필요하다.

### 확장 방향 (추정)

`order.return_requested` 이벤트 구독 → 반품 아이템 금액 합산 → 잔여 주문금액이 무료배송 기준 이하인지 평가 → 해당 시 `OrderShippingMethodAdjustment` 취소 + 배송비 복원 트랜잭션 추가.

이 흐름은 OrderChange 패턴으로 구현하는 것이 Medusa 아키텍처와 일치한다.

---

## 부분환불 vs 전액환불

| 구분 | 처리 |
|------|------|
| 부분환불 | `refundPaymentWorkflow`에 `amount` 지정. 한도 검증 후 해당 금액만 Refund 생성 |
| 전액환불 | `amount` 생략 시 `payment.amount` 전체가 사용됨 |

두 경우 모두 결제 프로바이더에 실제 환불 요청을 보내는 흐름은 동일하다.

---

## 재고 복원

`confirmReturnReceiveWorkflow`에서 정상 입고(`RECEIVE_RETURN_ITEM`) 수량만 `adjustInventoryLevelsStep`으로 재고에 복원된다. 파손 입고(`RECEIVE_DAMAGED_RETURN_ITEM`)는 `damaged_quantity`만 기록되고 재고에 추가되지 않는다.

## 개입 모듈 요약

| 모듈 | 역할 |
|------|------|
| `ORDER` | Return, ReturnItem, OrderChange, OrderTransaction 생성·관리 |
| `PAYMENT` | Refund 엔티티 생성, 결제 프로바이더 환불 API 호출 |
| `FULFILLMENT` | 반품 Fulfillment 생성(반품 배송 라벨) |
| `INVENTORY` | 재고 복원 (`adjustInventoryLevelsStep`) |
